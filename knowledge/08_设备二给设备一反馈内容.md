# 设备二给设备一反馈后的回执内容

最后更新：2026-07-14

本文回答的问题是：设备二给设备一返回决策帧后，设备一是否会把这一拍执行完后的反馈再回给设备二，以及当前工程中支持哪些反馈内容。

> 文件名按“设备二给设备一反馈内容”保留。严格按链路说，本文重点是“设备二发出决策帧后，设备一回给设备二的回执/执行反馈”。

## 结论

当前工程**支持设备一到设备二的反馈接收链路**，但它不是强制的“每一拍必须回一个执行完成确认”的同步协议。

设备二发送决策帧后，会通过同一个 TCP JSON Lines 连接非阻塞轮询设备一返回的 JSON 消息。没有反馈时，设备二不会等待阻塞，而是继续按下一帧设备一态势输入进行决策。

也就是说，当前闭环由两部分共同完成：

1. 设备一下一拍继续上报敌我态势，设备二据此重新规划。
2. 设备一可选返回 `plan_ack`、`execution_report`、`uav_status` 等回执，设备二据此记录接收状态、执行状态或触发重分配。

## 代码入口

### `station/exporter.py::PlannerExporter.maybe_publish(env, force=False)`

职责：设备二决策帧发布入口，同时负责轮询设备一反馈。

执行顺序：

```text
maybe_publish(env)
  -> _poll_feedback(env)       # 发送前先拉一次历史反馈
  -> _should_publish(...)
  -> PlanFrameBuilder.build(...)
  -> _payload_from_frame(...)
  -> _send_frame(...)
  -> _poll_feedback(env)       # 发送后再拉一次快速反馈
```

关键点：

1. 反馈是异步处理，不会阻塞主循环。
2. 设备二会在发送前后都调用 `_poll_feedback(env)`。
3. 发送成功后才会记录 `last_published_input_key`，避免发送失败时误认为该输入帧已闭环。

### `station/exporter.py::_poll_feedback(env)`

职责：从传输层读取设备一反馈，并交给反馈处理器。

调用链：

```text
_poll_feedback(env)
  -> self.socket.poll_feedback()
  -> self.feedback.process(env, events)
```

### `station/socket_client.py::PlannerSocketClient.poll_feedback()`

职责：从 TCP socket 中非阻塞读取设备一返回的 JSON Lines 消息。

处理方式：

1. 使用 `select.select(..., timeout=0.0)` 检查是否有数据可读。
2. 从 socket 读取字节流。
3. 按 `\n` 拆分 JSON Lines。
4. 每一行解析成 `dict` 后返回给上层。

如果没有消息，直接返回空列表，不影响设备二继续运行。

### `station/feedback.py::Device3FeedbackHandler.process(env, events)`

职责：解析设备一反馈，并把必要状态写回设备二环境。

虽然类名仍是历史命名 `Device3FeedbackHandler`，在当前两设备结构下可以理解为“设备一执行侧反馈处理器”。

当前支持三类反馈：

```text
plan_ack
execution_report
uav_status
```

## 反馈类型一：`plan_ack`

用途：确认设备一是否收到或接受设备二发出的决策帧。

示例：

```json
{
  "msg_type": "plan_ack",
  "plan_seq": 12,
  "accepted": true
}
```

如果设备一拒收：

```json
{
  "msg_type": "plan_ack",
  "plan_seq": 12,
  "accepted": false,
  "reason": "schema_version unsupported"
}
```

对应代码：

```text
station/feedback.py::Device3FeedbackHandler.process(...)
  -> _handle_plan_ack(event)
```

当前处理效果：

1. 记录 `self.last_ack_seq = plan_seq`。
2. 如果 `accepted=false`，写一条 `[PLAN]` 日志。
3. 不会因为拒收自动释放任务或重分配。

## 反馈类型二：`execution_report`

用途：反馈某架 UAV 对某条任务/航点/动作的执行结果。

这是当前最关键的反馈类型，因为失败或中止会触发设备二重分配。

示例：

```json
{
  "msg_type": "execution_report",
  "plan_seq": 12,
  "uav_id": "UAV-1",
  "drone_id": 1,
  "assignment_id": "assign_UAV-1_0003",
  "status": "failed",
  "reason": "航点不可达"
}
```

对应代码：

```text
station/feedback.py::Device3FeedbackHandler.process(...)
  -> _handle_execution_report(env, event)
```

### 失败/中止

如果：

```text
status in ("failed", "aborted")
```

设备二会执行：

1. 根据 `drone_id` 或 `uav_id` 匹配内部 UAV。
2. 把该 UAV 标记为临时不可用：

```text
it["device3_temporarily_unavailable"] = True
it["device3_failed_until"] = sim_now + failed_cooldown_sec
it["device3_failure_reason"] = reason
```

3. 调用 `_release_failed_binding(env, it)` 释放当前任务绑定。
4. 调用 `_trigger_reassignment(env)`，进一步触发：

```text
simulation/main.py::_force_task_reassignment(...)
```

结果：设备二会尝试把原目标重新分配给其他可用 UAV。

### 正在执行/完成

如果：

```text
status in ("completed", "engaging", "en_route", "executing")
```

设备二会：

1. 清除该 UAV 的临时不可用标记。
2. 清空 `device3_failure_reason`。
3. 保留最新执行报告：

```text
it["device3_last_execution_report"] = dict(event)
```

注意：当前代码里，`completed` 不会单独把整个任务置为完成。真实任务完成仍主要依赖设备一下一帧态势更新，或本地仿真中的命中/捕获/突防判定。

## 反馈类型三：`uav_status`

用途：同步设备一执行侧的 UAV 状态缓存，例如执行状态、电量、故障等。

示例：

```json
{
  "msg_type": "uav_status",
  "uav_id": "UAV-1",
  "drone_id": 1,
  "status": "en_route",
  "battery": 82,
  "fault": ""
}
```

对应代码：

```text
station/feedback.py::Device3FeedbackHandler.process(...)
  -> _handle_uav_status(env, event)
```

当前处理效果：

1. 根据 `drone_id` 或 `uav_id` 匹配内部 UAV。
2. 保存完整状态：

```text
it["device3_last_uav_status"] = dict(event)
```

3. 如果存在 `fault` 字段，写入：

```text
it["device3_failure_reason"] = str(event.get("fault") or "")
```

4. 如果该 UAV 之前被标记为临时不可用，且冷却时间已到，会自动恢复可用。

## 设备一反馈如何匹配设备二内部 UAV

匹配逻辑在：

```text
station/feedback.py::Device3FeedbackHandler._find_interceptor(env, event)
```

匹配字段：

1. 优先看 `drone_id`。
2. 再看 `uav_id`。
3. 映射关系来自 `core.common.PLAN_EXPORT["uav_id_map"]`，解析函数是：

```text
station/contracts.py::parse_uav_id_map(...)
```

因此联调时建议设备一回执尽量带上：

```json
{
  "uav_id": "UAV-1",
  "drone_id": 1
}
```

这样最容易和设备二内部 `env.interceptors[*]` 对齐。

## 和“每一拍执行完反馈”的关系

当前工程不是这种严格时序：

```text
设备一态势帧 N
  -> 设备二决策帧 N
  -> 设备一执行完 N 后必须反馈 N
  -> 设备二才能处理 N+1
```

当前工程更接近这种异步闭环：

```text
设备一态势帧 N
  -> 设备二决策帧 N
  -> 设备二继续等待下一拍态势
  -> 如果设备一同时回 plan_ack / execution_report / uav_status，则设备二顺手处理
  -> 设备一态势帧 N+1
  -> 设备二基于最新态势继续规划
```

所以，设备一可以每拍都回，也可以只在接收失败、执行失败、状态变化时回。设备二代码都能处理。

## 建议的最小联调反馈

如果设备一暂时只想实现最小闭环，建议先支持两类：

### 1. 收帧确认

```json
{"msg_type":"plan_ack","plan_seq":12,"accepted":true}
```

作用：确认设备一确实收到设备二决策帧。

### 2. 执行失败回报

```json
{
  "msg_type": "execution_report",
  "plan_seq": 12,
  "uav_id": "UAV-1",
  "drone_id": 1,
  "status": "failed",
  "reason": "航点不可达"
}
```

作用：触发设备二释放当前 UAV，并把任务重新分给其他 UAV。

后续再补充：

```json
{
  "msg_type": "uav_status",
  "uav_id": "UAV-1",
  "drone_id": 1,
  "status": "executing",
  "battery": 82
}
```

用于做执行侧状态展示和故障缓存。

## 当前限制

1. `plan_ack accepted=false` 只记录日志，不触发自动重分配。
2. `execution_report completed` 只清除失败标记，不直接判定全局任务完成。
3. 反馈接收是非阻塞轮询，不保证每一帧发送后立刻收到对应回执。
4. 历史命名里仍有 `Device3`、`device3_*`，当前可按“设备一执行侧”理解。
