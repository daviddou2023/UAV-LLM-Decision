# 09 大小模型融合决策改造思路

最后更新：2026-07-21

## 目标定位

当前项目中，大模型主要是“指挥副官”：负责态势播报、对话建议和少量任务约束解析；真正的任务分配、路径规划、避碰和回发决策帧仍由传统算法完成。未来若要实现真正的大模型决策，建议采用“地面大模型 + 机载小模型 + 传统算法安全兜底”的三层架构。

目标不是一次性替换现有算法，而是让模型逐步接管可解释、可验证的决策层：

1. 地面大模型负责全局态势理解、目标优先级、任务分配、编队意图和高层路径意图。
2. 机载小模型负责断链/干扰时的本地应急决策，例如继续拦截、返航、悬停、绕开干扰区、寻找最近安全航点。
3. 传统算法继续负责安全约束、碰撞规避、飞行边界、最低可行路径和模型输出校验。

## 现有代码判断

### 当前 LLM 位置

- `decision/llm_kit.py::BattlefieldAnalyst`：通过 OpenAI 兼容接口调用本地模型，主要生成一句话态势告警和副官对话回复。
- `decision/llm_task_constraints.py`：把自然语言解析为结构化约束，例如 `reserve_count`、`target_priority`、`preferred_sector`、`avoid_jam`、`max_active_count`。
- `simulation/main.py::_apply_llm_task_constraints_from_command()`：把解析出的 LLM 约束写入 `env.llm_task_constraints`。
- `simulation/main.py::_sync_llm_task_constraints_to_assigner()`：把约束同步给 `InterceptionAssigner.task_constraints`。

也就是说，当前 LLM 没有直接输出完整任务表或路径表，只是影响传统分配器的参数。

### 当前传统决策位置

- `simulation/main.py::InterceptionEnvironment.step(dt)` 是核心 tick，按顺序完成输入同步、LLM 约束、任务分配、起飞、干扰处理、路径/运动更新和本地判定。
- `decision/cooperation.py::InterceptionAssigner.update()` 负责撞击模式下的主拦截机/随动机分配。
- `simulation/main.py::_update_barrier_assignments()` 和 `_update_net_assignments()` 负责列阵/网阻模式编组。
- `decision/deconfliction.py::DeconflictionController.plan_local_motion()` 负责局部路径、安全间隔、绕飞和等待放行。
- `simulation/main.py::_move_interceptors(dt)` 根据任务状态刷新 `path_plan`，后续输出层只采样这些路径。

### 当前稳定协议边界

- `station/contracts.py::PlanFrameBuilder.build()` 是完整决策帧边界。
- `station/query.py::decision_output_frame_from_plan_frame()` 从同一份 `PlanFrame` 裁剪设备一主消费的精简帧。
- `station/exporter.py::PlannerExporter.maybe_publish()` 按设备一输入帧触发回发。

未来模型决策最好仍然写回 `env.interceptors[*].target_id/role/poi/path_plan` 等现有状态，再复用 `PlanFrameBuilder` 生成输出，不要直接另造一套回发协议。

## 建议总体架构

```text
设备一态势帧
  -> perception 输入归一化
  -> DecisionStateSnapshot 战场状态快照
  -> 决策策略层 DecisionPolicy
       -> GroundLargeModelPolicy  地面大模型，全局决策
       -> OnboardSmallModelPolicy  机载小模型，断链/干扰自治
       -> RuleBasedPolicy         传统算法兜底
  -> SafetyGate / DecisionValidator
       -> 编号校验、资源校验、禁飞/干扰区校验、碰撞/航线约束
  -> 写回 env 任务状态和 path_plan
  -> PlanFrameBuilder
  -> decision_output_frame
  -> 设备一执行
```

这里的核心改造是新增“决策策略层”，让 `simulation/main.py` 不再直接写死调用 `assigner.update()`、`_update_barrier_assignments()`、`_update_net_assignments()`，而是调用一个统一策略接口。传统算法先作为默认策略保留，大模型和小模型作为可替换策略逐步接入。

## 决策策略接口建议

建议在 `decision/` 下新增窄接口，例如：

```python
class DecisionPolicy:
    def decide(self, snapshot: DecisionStateSnapshot, context: DecisionContext) -> DecisionProposal:
        ...
```

其中：

- `DecisionStateSnapshot`：从 `env` 裁剪出的模型输入，不直接暴露整个 `InterceptionEnvironment`。
- `DecisionContext`：包含当前模式、链路状态、干扰状态、策略来源、时间戳、历史任务摘要。
- `DecisionProposal`：模型或算法输出的结构化决策建议。

建议 `DecisionProposal` 不直接等同于飞控协议，而是保持设备二内部语义：

```json
{
  "policy_source": "ground_llm|onboard_slm|rule",
  "decision_mode": "global|degraded|fallback",
  "assignments": [
    {
      "uav_internal_id": 0,
      "target_internal_id": 1,
      "mission_type": "intercept",
      "role": "primary",
      "formation_role": null,
      "priority": 0.92,
      "reason": "目标接近突防线且当前无人拦截"
    }
  ],
  "route_intents": [
    {
      "uav_internal_id": 0,
      "intent": "intercept|return_home|hold|avoid_jam|search",
      "reference_point": {"x": 1000, "y": 8000, "z": 28},
      "speed_hint_mps": 24.0
    }
  ],
  "constraints": {
    "avoid_zones": [],
    "max_active_count": 6,
    "reserve_count": 2
  }
}
```

这样做的好处是：模型输出仍然需要经过校验和传统路径层转换，避免直接生成不可飞航点。

## 大模型接管路径

### 阶段 1：大模型只输出结构化高层决策

先不要让大模型直接输出密集航点，而是输出：

- 目标优先级排序。
- 哪架 UAV 打哪个目标。
- 任务类型：撞击、列阵、网阻、搜索、返航、等待重分配。
- 编队角色：主拦截、随动、列阵槽位、网阻槽位。
- 干扰规避约束。

现有 `decision/llm_task_constraints.py` 只支持少量约束，可扩展为“结构化决策解析器”，但职责仍应保持纯解析，不直接改 `env`。

### 阶段 2：大模型输出 DecisionProposal

新增 `GroundLargeModelPolicy`，将战场快照转为 prompt，请求大模型输出严格 JSON。输出后交给 `DecisionValidator` 校验：

- UAV 编号必须存在且可用。
- target 编号必须存在且处于活动态。
- 同一 UAV 不能绑定多个目标。
- 同一目标的角色数量符合模式约束。
- 干扰区内 UAV 不可继续被地面模型调度。
- 如果路径意图穿越禁飞/干扰区，必须回退到传统绕飞。

校验通过后再写回 `env`，继续复用 `_move_interceptors()` 和 `DeconflictionController` 生成局部可执行路径。

### 阶段 3：大模型参与路径意图，不直接替代局部规划

大模型可以输出 `route_intent`，例如“绕开左侧干扰区，从东侧接敌”“失联风险高，改为返航/悬停”。但具体航点仍由 `decision/deconfliction.py` 和现有 `_update_route_plan()` 生成。

原因：当前 `PlanFrameBuilder` 只采样 `path_plan`，且局部避碰、起降队列、机巢通道、返航高度等细节都在传统路径层里。直接让 LLM 输出航点，会绕开大量安全规则。

## 小模型上机思路

小模型不应训练成“完整地面指挥官”的复制品，而应聚焦断链后的本机自治能力。

### 小模型输入

机载小模型输入应比地面大模型更小：

- 本机状态：位置、速度、航向、电量/续航、任务状态、当前目标。
- 局部目标：最近若干敌方目标或最后一次地面站下发目标。
- 链路状态：正常、降级、断链、干扰强度、断链时长。
- 安全约束：禁飞区、干扰区、返航点、最大速度/高度。
- 最近一帧地面决策：assignment、route intent、next_command_point。

### 小模型输出

建议输出离散高层动作，而不是完整连续航点：

- `continue_task`：继续当前拦截/编队任务。
- `hold`：原地悬停或低速保持。
- `return_home`：返航。
- `avoid_jam`：绕开干扰区。
- `search_last_target`：沿最后目标点搜索。
- `request_reconnect`：链路恢复后请求地面重分配。

再由机载传统控制/路径模块把动作转换为安全航点。这样更容易训练、验证和部署。

## 知识蒸馏闭环

### 数据采集

需要先给现有工程增加决策日志采样能力，记录每个 tick 的：

- 输入态势：敌方目标、我方 UAV、链路/干扰状态、设备一输入帧号。
- 地面大模型输出：结构化 `DecisionProposal`。
- 传统算法输出：当前 `assigner`、编队分配、`path_plan`、`PlanFrame`。
- 执行结果：是否命中、是否突防、是否进入干扰区、是否触发重分配。
- 人工/规则评分：成功、失败、风险、不可执行原因。

可以优先在 `station/exporter.py` 或新增 `decision/decision_trace.py` 中记录 JSON Lines，不影响现有 TCP 回发。

### 蒸馏样本格式

建议训练样本拆成两类：

1. 全局决策样本：训练小模型理解大模型的目标优先级和任务选择。
2. 断链自治样本：训练小模型在地面站不可达时选择安全动作。

样本示例：

```json
{
  "input": {
    "self": {"uav_id": "uav_01", "state": "intercepting", "link": "lost"},
    "local_targets": [],
    "last_ground_assignment": {"target_id": "target_002", "mission_type": "intercept"},
    "jam": {"active": true, "zone": "JAM-A", "loss_sec": 6.5}
  },
  "teacher_output": {
    "action": "hold",
    "reason": "链路彻底中断且目标观测不可用，优先悬停等待重连"
  }
}
```

### 训练路线

1. 先用规则算法 + 人工标注生成基础样本，建立安全动作边界。
2. 接入地面大模型，批量生成结构化决策和解释。
3. 用执行结果过滤样本，只保留成功率高、校验通过、风险低的决策。
4. 微调小模型，让它模仿大模型在断链场景下的动作选择。
5. 用仿真回放评估小模型，不能只看文本相似度，要看任务成功率和安全违规率。

## 断链和干扰模式切换

现有代码已有干扰相关状态：

- `create_interceptor()` 中有 `jammed_by_interference`、`jam_zone`、`jam_since`。
- `simulation/main.py::_interference_phase()` 将干扰分为 `degraded` 和 `lost`。
- `simulation/main.py::_maybe_auto_llm_interference_replan()` 当前会触发 LLM 侧重规划。

未来建议把它升级为正式链路状态机：

```text
CONNECTED
  -> DEGRADED：链路抖动，地面大模型仍可下发，但降低更新频率
  -> LOST：地面站不可达，机载小模型接管本机动作
  -> RECOVERING：链路恢复，上传本机状态和小模型动作历史
  -> CONNECTED：地面大模型重新全局分配
```

断链后，小模型只能控制本机或本编组内有限协同，不应越权重分配全局任务。链路恢复后，设备二应把小模型自治期间的动作记录进入蒸馏数据和评估日志。

## 建议分阶段实施

### 第一阶段：只做决策数据化，不改变行为

- 新增 `DecisionStateSnapshot`，从 `env` 裁剪模型输入。
- 新增 `DecisionProposal` 数据结构。
- 新增 `RuleBasedPolicy`，内部仍调用现有 `assigner.update()`、编队分配和路径流程。
- 新增 `DecisionTraceLogger`，记录输入、输出和结果。
- 输出仍走现有 `PlanFrameBuilder` 和 `decision_output_frame`。

验收：行为与当前传统算法基本一致，但每帧有可训练数据。

### 第二阶段：大模型影子决策

- 新增 `GroundLargeModelPolicy`，只在后台生成建议，不写回 `env`。
- 将大模型输出与传统算法输出对比，记录差异。
- 增加结构化 JSON 校验、编号校验和安全约束校验。
- 人工审核典型样本，形成蒸馏数据。

验收：大模型建议可解析、可校验、可解释，但不影响真实回发帧。

### 第三阶段：大模型有限接管

- 允许大模型接管目标优先级、任务绑定和编队意图。
- 传统算法仍负责路径生成、避碰、返航和兜底。
- 若大模型超时、JSON 不合法、校验失败，自动回退 `RuleBasedPolicy`。
- `PlanFrame` 中可增加 `policy_source`、`policy_confidence`、`fallback_reason` 等调试字段；若涉及设备一协议消费，需要同步更新协议文档。

验收：同场景下大模型决策能提升或至少不降低命中率、安全性和资源利用率。

### 第四阶段：小模型断链自治

- 定义机载小模型输入/输出 schema。
- 训练小模型输出离散动作。
- 仿真断链场景，让小模型在 `LOST` 状态接管本机动作。
- 设备二链路恢复后处理小模型自治历史，必要时触发重分配。

验收：断链情况下小模型能安全保持、返航或继续有限任务，不造成碰撞、越界或错误目标攻击。

### 第五阶段：闭环迭代

- 用真实联调和仿真回放持续补充蒸馏数据。
- 将成功案例、失败案例、边界案例分开训练和评估。
- 建立版本化评测集，每个模型版本必须通过固定场景。
- 保留传统算法作为长期安全兜底。

## 代码落点建议

| 目标 | 建议文件 | 说明 |
| --- | --- | --- |
| 模型输入快照 | `decision/state_snapshot.py` | 从 `env` 裁剪，不暴露可变大对象 |
| 模型输出协议 | `decision/proposal.py` | 定义 `DecisionProposal` 和校验辅助 |
| 策略接口 | `decision/policies.py` | `RuleBasedPolicy`、`GroundLargeModelPolicy`、`OnboardSmallModelPolicy` |
| 输出校验 | `decision/validator.py` | 编号、资源、任务、干扰区、安全约束校验 |
| 数据记录 | `decision/decision_trace.py` | JSON Lines 训练/评估数据 |
| 链路状态 | `decision/link_state.py` 或 `perception/link_status.py` | 统一通信状态，不只依赖 demo 干扰字段 |
| 主循环接入 | `simulation/main.py` | 逐步把硬编码分配调用替换为策略层调用 |
| 输出扩展 | `station/contracts.py` | 如需增加 `policy_source` 等字段，从 `PlanFrame` 扩展 |

## 不建议做的事

- 不建议让大模型直接输出设备一飞控 `commands[]`，这会绕开现有 `PlanFrameBuilder`、绑定校验和路径安全层。
- 不建议让小模型承担全局任务分配，断链后它没有完整战场态势。
- 不建议删除传统算法。模型接管后，传统算法仍是安全兜底和数据生成基线。
- 不建议把训练数据记录写在 UI 或 Redis 显示接口中，避免污染现有联调链路。
- 不建议一次性重构 `simulation/main.py` 超大类，应先以薄适配层接入。

## 关键风险

1. 模型幻觉：输出不存在的 UAV/target 编号。必须做结构化校验。
2. 延迟：地面大模型可能慢于设备一输入帧频率。需要超时回退传统策略。
3. 安全：模型输出可能穿越干扰区、禁飞区或导致近距离冲突。必须经过传统路径/避碰层。
4. 数据偏差：只用传统算法蒸馏会让小模型复制传统算法缺陷。需要混入大模型、人工审核和失败反例。
5. 断链权限：小模型只能做本地安全自治，链路恢复后必须接受地面全局重分配。
6. 协议扩展：若设备一要消费模型来源/置信度/解释字段，需要同步更新 `knowledge/device2-to-device3-interface.md`。

## 推荐近期最小落地

近期最小可行路线：

1. 先新增 `DecisionStateSnapshot` 和 `DecisionTraceLogger`，只记录、不改变当前行为。
2. 把当前传统算法输出包装为 `RuleBasedPolicy` 的 `DecisionProposal`。
3. 让地面大模型进入影子模式，生成同格式 `DecisionProposal`，只做对比和数据积累。
4. 选取干扰/断链场景，整理小模型训练 schema。
5. 等大模型 JSON 输出稳定后，再考虑有限接管目标优先级和任务绑定。

这个顺序能最大程度复用现有工程的输入、分配、路径、PlanFrame 输出和设备一联调链路，同时为后续知识蒸馏和机载小模型部署留下清晰边界。
