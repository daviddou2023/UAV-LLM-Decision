# 设计原则

最后更新：2026-07-03

本文件记录项目代码设计约束。新增接口和重构时优先遵守这里的原则；若与现有稳定实现冲突，以最小可工作的兼容改动为准。

## SOLID 摘要

参考资料：百度百家号文章《干货：面向对象设计的SOLID原则》，发布时间 2022-10-23 23:30，链接：`https://baijiahao.baidu.com/s?id=1747492023134059981&wfr=spider&for=pc`。

- SRP，单一责任原则：一个模块只承担一个清晰职责，变化原因尽量单一。
- OCP，开放封闭原则：稳定逻辑对扩展开放，对无关修改关闭；新能力优先通过窄适配层接入。
- LSP，里氏替换原则：替代实现必须满足调用方已有约定，不能让上层为了某个实现写特殊分支。
- ISP，接口隔离原则：接口要小而专，调用方不依赖不需要的方法和字段。
- DIP，依赖倒置原则：高层策略依赖抽象或稳定契约，细节实现依赖这些契约。

这些原则不是机械指标。实际修改时以可运行、可联调、可维护为目标，避免为了原则增加无用抽象。

## Ponytail 优先

编码默认采用 `ponytail` 思路：选择能满足当前真实需求的最小实现，而不是为未来可能性提前铺结构。

执行顺序：

1. 判断这个改动是否真的需要存在；纯猜测需求不提前实现。
2. 优先复用仓库已有函数、状态字段、协议结构和调用链。
3. 优先使用 Python 标准库和当前已安装依赖，不为几行逻辑新增依赖。
4. 能通过小函数或一处改动解决时，不新增服务层、抽象层或配置层。
5. 非平凡逻辑至少保留一个最小可运行检查；简单改名、注释和文档改动不强行加测试。

`ponytail` 不等于省略必要质量：输入边界、错误处理、数据不丢失、安全约束、设备联调协议兼容性不能为了“少写代码”被删掉。

## Ponytail 与 SOLID 的配合

- 先用 `ponytail` 控制代码量和文件数量，再用 SOLID 检查职责边界。
- SRP 用来防止“最小实现”变成万能函数；一个函数只做一类事情。
- OCP 用来保护稳定算法；新增接口优先包一层适配，不直接改核心分配逻辑。
- ISP 用来约束接口返回；只暴露调用方需要的字段，完整 `PlanFrame` 可作为调试附带信息。
- DIP 用来保持服务层依赖稳定契约；HTTP/TCP 包装层应依赖稳定的接口/转接模块，不要直接散落读取 `env` 内部细节。

## 本项目落地规则

- 当前主链路是设备二回发设备一的 `decision_output_frame`；历史地面站旁路转接层（实现位于 `station/plan_bridge.py`）只作为兼容/调试薄转接层。
- 任务分配算法仍归 `decision/cooperation.py`、`simulation/main.py` 中的既有分配流程所有；接口层不得复制一套并行算法。
- `PlanFrameBuilder` 是设备二完整决策契约的稳定边界；新增查询或精简输出接口优先复用它，而不是另造字段结构。
- HTTP、TCP JSON Lines、Redis 调试镜像属于服务/传输封装，不和核心 Python 查询函数混在同一职责里。
- 新增函数优先保持小而直接：一个函数做一次约束应用、一次查询或一次格式整理。
- 只有出现两个以上真实调用点或明显重复约束时才抽象公共层；预留式抽象不进入代码。
- 注释使用中文描述边界和意图；协议名、字段名、类名、函数名按代码原样保留。
